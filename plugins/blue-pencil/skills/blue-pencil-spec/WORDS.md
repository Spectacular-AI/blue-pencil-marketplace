# Words for the user

The user has never heard the tool's words. Say the plain thing; keep the tool's word for files, tool
calls and your own notes.

| The tool's word | Say to the user |
|---|---|
| spec | "the rules for a good [email]", or "the list of rules" |
| check | "a rule's result" |
| value, score | "a score from 0 to 1: the higher, the surer the rule is met" |
| outcome `fail`, `pass` | "the rule failed", "the rule passed" |
| decisive | "sure" |
| borderline | "not sure either way, so read that part yourself" |
| edges, strictness | "how sure a result must be before it counts as failed or passed" |
| part, part path | the heading's own name: "the Limits section" |
| assertion, `must_say`, `should` | the rule itself, in a sentence: "it must say why the date moved" |
| package, item | "a built-in list of [overused phrases]" |
| known-good, known-bad, held back | "examples you're happy with", "examples with a fault", "examples I set aside to test on" |
| frontmatter | "the block of settings at the top of the file" |
| review (the tool) | "checking the document against the rules" |

## A message to the user

- **One thing a message**: one goal, one question, or one set of flags.
- **A question** is written toward [question.spec.yaml](question.spec.yaml): a new one in up to three
  short sections (where we are, what I noticed, the question); a quick follow-up on the user's last
  answer in one.
- **Any other message puts its point first**, then at most a few lines. What you found along the way
  stays in your notes.
- **Quote their document** when you ask about it; a quoted line is easier to judge than a description.
- **Offer two or three options** when you offer any.
- **A file's path** only when they need to open the file.
